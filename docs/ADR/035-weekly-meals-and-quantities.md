# ADR 035 — Weekly meal planning and measured shopping review

User approved per-serving quantities, weekly meal planning and combined shopping review. Core workflows remain offline; optional existing Apple on-device generation supplies proposals. No network model or new transport.

MealPlanEntry adds optional ingredientAmountsPerServing, a dictionary keyed by the meal's exact ingredient names with canonical decimal/unit strings. This is recipe metadata within the existing normalized meal entity, not a household blob. Quantities are optional; old records remain valid and unknown. SwiftData uses an additive optional property and the explicit backup/CloudKit payload adds the optional field. Shared clients should upgrade together to preserve it on edits. No retroactive quantities or destructive migration. Per-serving amounts are validated; quantity editor drops entries for removed names.

Weekly screen shows seven civil days and breakfast/lunch/dinner slots. Manual editing uses existing local editors. Suggest a week asks the existing on-device meal service for ideas; when unavailable it uses labelled built-in candidates. Candidate rotation can repeat dishes. The user can swap, deselect and change servings before one atomic save. Existing occupied slots are preserved, with commit-time rechecks; no persisted plan is overwritten by a proposal. Amounts are not inferred by generation. Date-bearing pantry packs rank candidates for earlier slots, but actual stock availability is checked separately.

Weekly shopping collects uncooked planned-meal demands, scales per-serving amounts and aggregates aliases. Known compatible quantities allocate remaining pantry stock once in chronological order, earliest-expiring packs first, excluding packs expired before the meal day. No mass/volume/count cross-conversion. Unknown recipe/pack quantities and mixed dimensions require explicit user review and do not produce a fabricated numeric shortage. Existing pending shopping entries are shown as already listed and skipped, with a direction to check their amounts; their quantity is not assumed sufficient. All new additions start unselected. Selecting an unknown-amount row adds only the name. Review does not change stock, meals, tasks or existing shopping amounts.

Confirmation recomputes rows and rejects a changed preview or different household, preventing stale local quantity decisions and duplicate add after review. Existing local-first commit/write-access guards apply; subsequent private/shared sync uses existing records. Concurrent offline multi-device shopping additions still use the existing sync conflict model, not a distributed inventory reservation system. No persistent stock reservation is implied by a planning preview.

Today keeps today's meals and adds open prep tasks linked to tomorrow's uncooked meals. Notification permissions and delivery semantics are unchanged. Tests use in-memory data; real household records are not cleared.
