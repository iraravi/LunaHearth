# ADR 033 — Cook a planned meal and review pantry usage

User approved the connected cooking workflow: recipe review, missing-shopping items, preparation tasks, completion and measured pantry use.

MealPlanEntry adds optional ingredientNames, preparationSteps, servings and cookedAt. HouseholdTask adds optional mealID. Fields are additive and included in the existing backup/custom CloudKit record payload adapters; old backups decode with nil fields. No automatic SwiftData CloudKit mirroring or external backend. Older clients cannot preserve new fields when editing: upgrade all collaborating devices. No destructive migration or historical ingredient inference. Old meal notes remain readable; edit the meal to add structured ingredients.

Inventory quantities use strict decimal parsing of canonical amount/unit text, preserving legacy descriptions. The editor offers measured g/kg/oz/lb, ml/l and pieces. Decimal conversion occurs only within mass, volume or count. Unknown descriptions and mass/volume conversion require manual review. The finish sheet defaults every pack to unchanged; users select measured usage, low stock or used up. No inferred serving-based consumption or automatic low-stock threshold. Remaining values are rounded to three decimal places. Existing low-stock flags stay until explicitly changed/restocked.

Finish validates meal/pack modification snapshots and every selected amount before one local transaction updates inventory, cookedAt and linked preparation completion. Repeat finish is rejected. Shared transport preserves these ordinary records; it is not a distributed serializable stock ledger. Simultaneous offline edits can still meet the existing record conflict rules; refreshing first and stale-snapshot rejection after sync reduce stale review. No claim of cross-device transactional locking. Cooked meals cannot be reopened for repeated deductions in this version.

Missing ingredient selection explicitly adds allowed meal ingredients to household shopping and rechecks active alias duplicates in one transaction. Pantry candidates account for recorded expiry. A matching pack does not prove sufficient quantity. Preparation is a normal household task with a user-selected instant and optional assignment; it survives offline and participates in normal sync/reminder export. An optional timed local alert asks for permission after task creation, schedules generic content and opens the linked meal. It is enabled only on the scheduling device. Existing scheduled alerts reconcile on active repository refresh, so observed task completion/deletion cancels them. Offline remote changes cannot cancel a device alert until received. Pending/already-delivered notifications never substitute for persisted tasks.

On-device AI can propose bounded preparation steps alongside ideas; user review/save remains required. Built-in curd rice, egg rice and banana oats include steps; other starters can be planned with user-entered steps. No model guesses inventory quantity or performs mutations. No receipt, recipe or household content leaves the device for inference.

Today shows a meal link, cooked state and next open preparation task. Saved Meals opens the cooking detail. UI supports native Dynamic Type and adaptive bounded content; no undocumented device APIs.
