# Bug scan — November 13, 2026 (2.0.2 build 85 working tree)

Scope: entire app, prioritising flows that can lose, duplicate or misstate household data.
Method: clean build warning sweep; pattern search over all 232 Swift files; close reading of the
repository core, receipt import, expenses, backup codec coverage, CloudKit sharing/merge, cleanup,
notifications and calendar/reminder date mapping; probe tests for suspected receipt regressions.
Not covered: line-by-line reading of every SwiftUI view, the full UI test suite, real devices.

## Findings

### 1. Item-code receipt rule drops all items when a header line says "TAX…" or "TOTAL…" — confirmed, regression in build 85
`ItemCodeReceiptDetails.usesItemCodes` now turns on for any line starting with 4+ digits (a street
address, a PIN code, a barcode). `productSection` then keeps only text above the first line starting
with SUBTOTAL/TAX/TOTAL. Indian GST bills print "TAX INVOICE" at the top, and stores such as
"TOTAL WINE & MORE" print TOTAL in the header, so every item is cut.
Probe: `1234 Anna Salai` + `TAX INVOICE` + two priced items → 0 items; `TOTAL WINE & MORE` +
`5100 Belt Line Rd` + `MERLOT 12.99` → 0 items. Effect: the receipt falls back to expense-only
(no wrong data), but itemization never works for these receipts.
Fix: cut only at a summary row that comes after the first item-code product row; require a coded
product row with a price, not any number-led line.

### 2. Store-name suggestion matches a catalog word inside a longer header — from code reading
`ReceiptPurchaseDetails.knownStore` accepts any catalog name found as a whole word in the first
five rows, so "TOTAL WINE & MORE" suggests "More" (an Indian catalog store), and a header that
contains "Target" as a word would suggest Target. The value is editable, but it is wrong.
Fix: in the header, accept a catalog name only when it is the whole row or the row's leading words.

### 3. Sharing cannot run for a home restored from a portable backup with documents or room scans — from code reading
`HouseholdSharingController.performSync`, `enable`, `applyCloudChanges` and `resolveCloudConflicts`
all call `makeBackup()`, which throws `attachmentsUnsupported` when any `DocumentRecord` or
`Room.roomPlanAssetPath` exists. These only come from a portable-backup restore today, so the
affected set is small, but such a home can never enable or continue sharing and the message does
not say why. Fix: build sync snapshots with attachment metadata excluded rather than refused.

### 4. Deleting an expense leaves its purchases marked as already recorded — from code reading
`deleteExpense` and Cleanup → Expenses delete the expense but keep `PurchaseEntry.expenseID`.
`receiptPurchaseCandidates` then reports `alreadyLinked`, so a later receipt cannot be attached to
those purchases (`alreadyExpensed`); the remaining choice, "Record this purchase", adds pantry stock
again. Re-scanning the identical receipt still works because its lines are already imported.
Fix: clear `expenseID` on linked purchases when their expense is deleted.

### 5. Turning "Record in Expenses" off and on loses scanned line amounts — from code reading
`ReceiptImportView` clears every line amount when the toggle is turned off and does not restore or
flag them when it is turned on again, so a verified item list silently loses its prices.

### 6. Pantry-only receipt imports date purchases today, not on the receipt date — from code reading
`importReceipt` uses `expense?.date ?? .now` for `purchasedDay` and purchase history, so importing
last week's receipt without recording an expense dates the purchase today even when the receipt
date was read.

## Areas checked and found clean
- Zero compiler warnings (clean build, Swift 6 strict concurrency); no `@unchecked Sendable`,
  `nonisolated(unsafe)`, `Task.detached` or `DispatchQueue` escapes; one `fatalError` at store init only.
- No money stored or summed as floating point; amount formatting only receives non-negative values.
- No swallowed SwiftData saves; every write goes through `commit` with rollback.
- Backup/sync codec maps every stored field except document files and room scans (refused by design).
- Every deletion the app can make is of a type other devices accept; CloudKit rejects others safely.
- Date-only values use stable day keys; appointment notifications pin the exact instant;
  reminder/calendar export uses the stored dates.
- Receipt import guards duplicate lines, changed matches, replayed receipts and double stocking.
- Unit tests: 407 / 77 suites pass on the current tree.

## Fixes — November 13, 2026

All six findings fixed in the working tree (not yet in a TestFlight build):

1. `ItemCodeReceiptDetails.isCodedProductRow` requires a code-led row that ends with a price-like token; the product section is cut only at a summary row after the first such product.
2. `ReceiptPurchaseDetails.knownStore` accepts a header store name only at the start of its row.
3. `LocalHouseholdRepository.makeSyncSnapshot()` is used by every sharing path; document files and room scans stay local and no longer block sync. Portable/iCloud backups still refuse attachments as before.
4. `deleteExpense` and Cleanup → Expenses clear `expenseID` on linked purchases (`unlinkPurchases(fromExpenses:)`). Receipt line keys are kept as replay protection.
5. The receipt screen keeps the scanned line amounts and restores them when "Record in Expenses" is turned back on.
6. `importReceipt(…, purchaseDate:)` dates pantry-only imports with the receipt date when it was read.

Validation: `BugScanRegressionTests` (7 tests) cover 1, 2, 3, 4 and 6; #5 is view state and was not unit-tested. 414 unit tests / 78 suites pass; Release builds; UI tests passed: receipt review/import, explicit inventory choice, bought-item linking, expense dashboard, expense-only receipt deletion, saved shopping stores.
